# 团队分工与交付边界

本表按 6 人设计。成员姓名和 GitHub 用户名由组长补入。标为“主责”的任务必须由对应成员主导，其他成员仍需参与评审和验收。

| 成员 | 主责模块 | 必须完成的交付 | 主要依赖 |
|---|---|---|---|
| 成员 A | 文献、网络模型与拓扑 | 维护 6 篇以上文献清单；重点分析至少 2 篇；实现 36 节点固定拓扑；写明模型假设、单位、与真实星座差异 | 无 |
| 成员 B | 业务、队列与分组转发 | 均匀/热点业务生成；分组大小、速率、随机种子；有限队列、排队与丢弃；生成可复现基础数据 | 成员 A 的拓扑接口 |
| 成员 C | 传播时延 Dijkstra | 实现最短传播时延路由；明确代价单位、更新周期和无路由处理；单元测试 | 成员 A、B |
| 成员 D | 队列加权与交通灯路由 | 实现综合传播时延和队列状态的路由；复现简化 TLR/Traffic Light 机制；说明保留、简化与来源 | 成员 A、B、C 的公共接口 |
| 成员 E | 实验编排、统计与绘图 | 统一配置；3 档以上负载、两类业务、每档至少 5 个种子；统计均值/波动；生成全部必需图；基础脚本 | C、D 的算法完成 |
| 成员 F | 集成、测试、报告与答辩 | 合并与回归测试；README 验收；整理结果；完成 3000 字以上报告和 AI 使用记录；按需制作 PPT | 全体 |

## 并行工作顺序

1. 组长在第一次会议中确认成员 A 至 F 对应姓名，并把 GitHub 用户名加入项目。
2. 成员 A 先提交拓扑字段和配置草案，成员 B 同时提交流量与队列字段草案。
3. 成员 C 和 D 在第 2 步的接口冻结后并行开发算法；共享修改必须发 PR 通知全员。
4. 成员 E 先搭建实验外壳和占位图，不等待算法全部完成；算法接入后再产生正式结果。
5. 成员 F 每周检查任务看板，合并后重新运行测试，避免最后一天集中集成。

## 共同责任

- 每人负责自己模块的单元测试、运行说明和 AI 使用记录。
- 每人都要审查至少一个其他成员的 PR。
- 实验参数或指标定义发生变化时，必须通知成员 E 和 F，并标记旧结果失效。
- 最终报告中的成员分工应与实际 PR、Issue 和提交记录一致。

## 可选任务

选做算法改进由成员 D 主导，参数敏感性分析由成员 E 主导。只有在全部必做项通过基础实验后才开始，避免选做任务挤占报告和复现工作。
